0.1 НАЗНАЧЕНИЕ
   sib-monitor следит за доступностью сайтов СИБУР и связанных ресурсов:
   HTTP-ответ, содержимое (Content Match), срок и цепочку SSL, срок оплаты домена.
   При сбое отправляет сообщения в Telegram и регистрирует инциденты. Для выбранных
   сайтов при длительном простое отправляет письмо об инциденте на заданные адреса.
   Дашборд показывает текущее состояние, аналитику, инциденты и календарь сроков.

   |каждые 60 с |   |4 ч + повтор 15м |   |09:00 SSL-отчёт|   |23:30 сводка  |  |03:00 логи  |

   | Отслеживаемые сайты (~50)     |      | Telegram Bot  |   | PostgreSQL (Amvera)           |
   | резерв: Globalping (только    |      | API           |   | logs (партиции), checks_agg,  |
   | при сетевой недоступности)    |      +---------------+   | latest_status, incidents,     |
   +-------------------------------+      | SMTP-сервер   |   | monitored_sites, app_meta,    |
                                          | (e-mail)      |   | email_notifications           |
                                          +---------------+   +-------------------------------+

   Ключевые решения:
   - Проверки выполняются в фоновых потоках, веб-запросы их не ждут.
   - Последнее состояние хранится в latest_status, дашборд читает только её
     (кэш 30 с).
   - SSL/WHOIS проверяются отдельно от HTTP: это медленные операции.
   - Резервная внешняя проверка (Globalping) подключается только при сетевой
     недоступности: таймаут, DNS, отказ соединения. Ошибка HTTP, TLS или контента —
     результат основной проверки.
   - Неполная цепочка достраивается по AIA. Самоподписанный сертификат или
     корпоративный CA с действующим сроком и верным именем — не ошибка, сайт помечается 🔓.
   - E-mail оповещения (monitor.12) работают независимо от Telegram: своё время простоя,
     свои получатели и переключатель на каждый сайт. Отправка — в фоновом пуле
     email-alert, проверки её не ждут.

0.7 ДЕТАЛЬНОЕ ОПИСАНИЕ РАБОТЫ

   HTTP-цикл (каждые 60 с):
   1. Загружается список активных сайтов, групп, порогов и настроек SSL/Content Match.
   2. Сайты проверяются параллельно (до 15 одновременно), у каждого свой таймаут
      (по умолчанию 8 с). HTTP 200 и 401 — Online. Для ключевых сайтов проверяется текст.
   3. Ошибки сертификата разбираются: если цепочка неполная — догрузка по AIA и повтор;
      если сертификат самоподписанный или выдан частным CA — проверяются срок и имя.
   4. Только при сетевой недоступности (таймаут, DNS, отказ соединения) делается
      резервная проверка из внешних точек: не чаще раза в 10 мин на сайт, в пределах
      часового лимита.
   5. Результаты попадают в буфер, затем в logs, checks_agg и latest_status.
   6. Счётчик неудач растёт; при достижении порога (по умолчанию 5 мин) отправляется
      🚨 DOWN со скриншотом и создаётся инцидент. При восстановлении приходит ✅ UP
      с реальной длительностью простоя из инцидента.
   7. E-mail: если у сайта включено «📧 Оповещать по e-mail» и простой (от первой
      неудачной проверки) достиг заданного числа минут (по умолчанию 15), на адреса
      сайта уходит письмо [ИНЦИДЕНТ]. Одно письмо за простой. При восстановлении —
      письмо [ВОССТАНОВЛЕН] с общей длительностью простоя. Каждое из двух писем
      включается отдельной независимой опцией (monitor.15): можно включить одно, оба
      или ни одного; по умолчанию оба включены. Если письмо об инциденте выключено,
      письмо о восстановлении уходит только после простоя дольше заданного времени.
      Для srm.sibur.ru и tms.sibur.ru письмо о восстановлении не отправляется никогда. Неопределённый результат
      проверки не считается ни сбоем, ни восстановлением. Каждое письмо пишется в
      email_notifications; после перезапуска открытые простои и отправленные письма
      восстанавливаются, письма не дублируются.

   SSL/WHOIS-цикл (раз в 4 ч, повтор для сайтов без данных — каждые 15 мин):
   1. Подключение к :443 из сети монитора (таймаут 8 с), проверка цепочки, срока и имени.
   2. При сетевой недоступности — данные TLS из внешней точки.
   3. Если данных нет, последний известный срок сохраняется, а в ячейке SSL появляется
      ⓘ с причиной (ssl_note).
   4. WHOIS — срок оплаты домена.

   Отчёты:
   - 09:00 МСК — SSL-сертификаты со сроком до 20 дней (свежая проверка).
   - 23:30 МСК — сводка релизов за день из CHANGELOG.md (улучшения, исправления, прочее).
     Повторы убираются: дословные пункты — всегда; пункты с одной темой
     `<!-- тема: имя -->` — остаётся пункт последнего релиза; пункты релизов, отменённых
     строкой `<!-- отменяет: версия -->`, не включаются. Служебные комментарии в текст
     сводки не попадают.
     Если релизов не было, сообщение не отправляется. Отправка однократная (app_meta).

   Отказоустойчивость:
   - Подключение к БД ограничено 10 с; /health читает БД в отдельном потоке и при
     зависании базы отвечает 503, а не блокирует приложение.
   - Ошибки воркеров логируются, циклы продолжаются.

1. АРХИТЕКТУРА
   - FastAPI + PostgreSQL (партиционированная) + Playwright + aiohttp + Chart.js + BCrypt
   - 5 фоновых потоков: check_worker (60с), ssl_whois_worker (4ч + повтор 15 мин),
     daily_report_worker (09:00), release_digest_worker (23:30), rotation_worker (03:00)
   - 15 API endpoints

2. БАЗА ДАННЫХ
   - logs: партиционированная по timestamp (авто-партиции на 3 мес вперед)
   - checks_agg: 5-мин агрегаты (uptime, avg/min/max response)
   - incidents: история падений с resolved статусом
   - monitored_sites: управляемый список с группами (key/stdo/external/self) + порог алерта
   - health: heartbeat воркера
   - latest_status: обычная таблица с последними результатами проверок.
     check_error — причина ошибки последней HTTP-проверки; очищается при восстановлении.
   - monitored_sites.http_timeout_seconds: индивидуальный HTTP-таймаут, целое число
     от 1 до 60 секунд, по умолчанию 8. Проверка диапазона есть в API и в БД.

3. DASHBOARD (/) — 4 вкладки
   - Список: группировка (Ключевые / СТДО / Внешние), sibur.ru всегда первый, KPI под каждой группой
     - Под статусом и в «Обратите внимание» показана причина: DNS, TLS, таймаут,
       отказ/сброс соединения, HTTP-код или Content Match.
     - Время проверки измеряется монотонными часами после выхода из очереди,
       включая чтение содержимого и ошибки; условные 25 секунд больше не подставляются.
   - Аналитика: Chart.js графики (14 дней), lazy load, кнопка "Показать все внешние"
   - Инциденты: последние 100 за 30д, первые 20 видны + кнопка, колонка Статус (Active/Resolved)
   - Календарь: SSL + домен, сортировка по дням, прокрутка если широкая таблица

4. KPI БЛОК
   - Доступно: online / total (danger если offline)
   - Uptime: 24ч / 30д (взвешенное среднее из checks_agg)
   - Ответ: 24ч / 30д
   - Инциденты: active + offline (danger если active>0, подпись "(N active)")
   - SSL <=20д: danger если есть
   - ⚠️ Обратите внимание: Offline + SSL <=20 + Задержка >15с + Active инциденты

       (включение возможно только при заданных адресах). В «Изменить»: флажок

       возникновении инцидента» и «Отправлять email-уведомление при восстановлении
       работоспособности» (по умолчанию оба; можно снять оба), адреса через «;» или «,»,
       «после, мин» (1–1440). У srm.sibur.ru и tms.sibur.ru второго флажка нет — вместо

   - Настройки → «E-mail оповещения»: общий выключатель, состояние SMTP, тестовое письмо.
   - Инциденты → «Журнал e-mail оповещений»: последние 50 писем и результат отправки.

6. TELEGRAM АЛЕРТЫ
   - Порог по умолчанию: 5 мин (настраивается в Управление → Порог мин для каждого сайта)
   - 🚨 DOWN: fail_count >= threshold + скриншот (3 сек после domcontentloaded)
   - ✅ UP: восстановление + скриншот + длительность (только если был DOWN алерт)
   - 🐢 Задержка: первая проверка дольше 15с (до 15с включительно задержка не начинается), следующая
     проверка — дольше 10с (подтверждение). Только после подтверждения отправляется сообщение.
     Если следующая проверка не дольше 10с, неуспешна или без результата, разовая задержка не сообщается
     (в логе — `[LATENCY PENDING]`). Отметка «Задержка» в строке сайта на панели — по последней проверке, дольше 15с.
   - ⚡ Скорость восстановлена: после подтверждённой задержки — первая проверка не дольше 10с. В сообщении —
     «Задержка длилась: N мин.»: от первой медленной проверки (начало задержки) до проверки с корректным
     откликом, минимум 1 мин. Если начало неизвестно (задержка началась до перезапуска приложения),
     длительность не указывается.
   - Задержка фиксируется только у сайтов с HTTP-таймаутом больше 15с: при таймауте по умолчанию (8с)
     долгий ответ считается Offline (таймаут), а не задержкой.
   - 🔔 SSL отчет: SSL <= 20 дней (09:00 МСК)
     - Перед отправкой сертификаты проверяются заново, без использования старого счётчика из latest_status.
     - Исключены неактивные сайты, self-monitoring и сайты с отключённой проверкой SSL.
     - Если актуальный срок получить не удалось, сайт пропускается в ежедневном Telegram-отчёте; причина остаётся в логах `[SSL REPORT SKIP]`. Старое число дней не используется. Если подтверждённых предупреждений нет, сообщение не отправляется.
     - Ежедневные напоминания сохраняются, пока сертификат входит в порог предупреждения.
   - 🧪 Тест скриншот: по кнопке (rate limit 30 сек/сайт)
   - Retry 3x, exponential backoff, логирование каждого вызова

7. SELF-MONITORING (https://sib-monitor-ankori.msk1.amvera.tech/)
   - Изолирован: не в KPI "Доступно", не в общей таблице dashboard, не в группах
   - Проверка: любой HTTP-ответ = Online (200), только timeout = Offline (0)
   - Алерты: порог 10 мин, помечены [SELF-MONITORING] в Telegram
   - Прежний адрес amvera.io отключается при старте; его история сохраняется.
   - Новый адрес проверяется по корневой странице; запрос авторизации (401) также означает Online.
   - Первичная очистка SM выполняется только один раз по маркеру sm_cleanup_v1, не при каждом старте.
   - Fallback Online: если нет в БД — показывает status=200
   - Вкладка только в Управлении (не на главном dashboard)

7a. E-MAIL ОПОВЕЩЕНИЯ (monitor.12)
   - monitored_sites: email_alert_enabled (по умолчанию FALSE), email_alert_to,
     email_alert_after_min (по умолчанию 15), email_alert_on_down и email_alert_on_up
     (monitor.15, по умолчанию TRUE — оба письма). При включении оповещения кнопкой в
     колонке, если обе опции были сняты, включаются обе (для srm/tms — только об инциденте).
   - При первом запуске monitor.12 оповещение включено для srm.sibur.ru и tms.sibur.ru:
     sap_sm@sibur.ru, более 15 мин простоя (однократно, маркер app_meta email_alert_seed_v1;
     дальнейшие изменения — только из админки).
   - srm.sibur.ru и tms.sibur.ru (email_alerts.NO_RECOVERY_SITES): письмо о восстановлении
     запрещено в коде — не отправляется, даже если в БД или запросе API указано on_up=TRUE;
     при каждом старте для них выставляется email_alert_on_up = FALSE. Письмо об инциденте
     остаётся. В письме об инциденте указано, что письма о восстановлении не будет.
   - Тема письма об инциденте: «[ИНЦИДЕНТ] <сайт> недоступен более N мин», высокий приоритет.
     Содержимое: сайт, адрес, состояние, начало простоя (МСК), длительность, последняя
     проверка, код ответа, причина, категория, порог, номер инцидента, ссылка на мониторинг.
   - Тема письма о восстановлении: «[ВОССТАНОВЛЕН] <сайт> доступен, простой X мин»,

=== ИНДИВИДУАЛЬНЫЙ HTTP-ТАЙМАУТ ===
Управление → Сайты → Изменить → Таймаут, с → Сохранить.
Текущее значение показано в колонке «Таймаут HTTP, с». Поле есть и при добавлении.
Допустимо 1–60 секунд; не путать с порогом инцидента в минутах.
Настройка сохраняется в БД и читается в начале следующего цикла, без перезапуска.
Это общий лимит HTTP-запроса: подключение, TLS, перенаправления и чтение ответа.
Тестер Content Match в админке использует то же значение; отдельного ограничения
чтения тела в 10 секунд больше нет. Текст таймаута показывает выбранный лимит.
При больших значениях цикл может стать длиннее минуты. Пороги инцидентов продолжают
использовать существующий счётчик неуспешных циклов; их логика здесь не менялась.
SSL/WHOIS, self-monitoring, скриншоты и отдельный NET DIAG сохраняют свои лимиты.

transportorder.sibur.ru, cp.tdms.sibur.ru/cp/, tst-stdo.tdms.sibur.ru/cp/,
bopp.sibur.ru, eshop.sibur.ru, srm.sibur.ru, resti.club, lsdts.sibur.ru,

ручных настроек при последующих запусках. SSL/CM, активность, пороги и история
не изменяются. Для отмены эксперимента установите нужным сайтам 8 секунд в админке.

## Неполная цепочка TLS (AIA)

Если сервер отдаёт только конечный сертификат без промежуточного, Python сообщает
«unable to get local issuer certificate», хотя браузер открывает сайт (он догружает
промежуточный сертификат по ссылке AIA «CA Issuers»). Монитор делает то же самое
(`tls_chain.py`): загружает промежуточный сертификат только с публичного адреса,
принимает его лишь при криптографической проверке до системного корня, добавляет в
общий SSL-контекст и повторяет проверку один раз. Срок и имя хоста по-прежнему
проверяются: истёкший или чужой сертификат остаётся ошибкой.

Для резервной внешней проверки (Globalping, ошибка `UNABLE_TO_VERIFY_LEAF_SIGNATURE`)
TLS считается подтверждённым, только если выдавший CA — проверенный промежуточный
сертификат из хранилища монитора, срок не истёк и имя хоста совпадает.
`certs/intermediates.pem` содержит промежуточные GlobalSign (RSA OV SSL CA 2018,
GCC R46 OV TLS CA 2025); при загрузке они тоже проверяются до системного корня.

Правильное исправление на стороне сайта — настроить на сервере полную цепочку
(конечный + промежуточный сертификат), иначе ошибки будут у API-клиентов,
мобильных приложений и curl.

## Самоподписанные сертификаты

Самоподписанный сертификат или сертификат от частного (непубличного) корня
(`self-signed certificate`, `self-signed certificate in certificate chain`, а также
`DEPTH_ZERO_SELF_SIGNED_CERT` / `SELF_SIGNED_CERT_IN_CHAIN` у Globalping) не считается
ошибкой. Монитор читает сертификат без проверки цепочки и проверяет то, что можно
проверить: срок действия и совпадение с именем сайта. Если всё в порядке, доступность
проверяется без проверки цепочки доверия, сайт остаётся Online, а в строке сайта
появляется пометка «🔓 самоподписанный сертификат» (в колонке цепочки — ⚠️, срок SSL
считается по самому сертификату). Просроченный самоподписанный сертификат или
сертификат на другое имя остаётся ошибкой TLS. Пометка снимается автоматически,
когда сайт начинает отдавать доверенный сертификат. Признак хранится в
`latest_status.ssl_self_signed`.

## Частный (корпоративный) CA и SSL для недоступных из Amvera сайтов

Если цепочку нельзя довести до публичного корня даже по AIA (например, сертификат выдан
корпоративным `SiburInfrastructureCAG1`), сертификат обрабатывается как самоподписанный:
при действующем сроке и совпадающем имени сайт Online с пометкой «🔓 самоподписанный
сертификат». Для Globalping это `UNABLE_TO_VERIFY_LEAF_SIGNATURE` с неизвестным выдавшим CA
(известные публичные промежуточные — из `certs/intermediates.pem` и AIA-кэша).

Если SSL-цикл не может подключиться к сайту из сети Amvera, срок и статус сертификата
берутся из одного измерения Globalping (раз в цикл SSL, 4 часа; только при включённой
проверке SSL). Это значение попадает и в утренний SSL-отчёт.

Признак «самоподписанный» HTTP-воркер записывает в `latest_status.ssl_self_signed` в
том же цикле, в котором он изменился (журнал `[TLS MARK]`).

## SSL: основная проверка, резерв и повтор (monitor.10)

SSL-проверка сначала выполняется из сети монитора (таймаут подключения 8 с). Globalping
используется, только если сайт недоступен по сети: таймаут, DNS, отказ соединения или
обрыв TLS-рукопожатия. Ошибка сертификата или рукопожатия при установленном соединении —
это результат основной проверки, Globalping её не подменяет. Если проверка SSL у сайта
выключена, сертификат не проверяется, а в подсказке ячейки SSL написано «Проверка SSL
отключена в настройках сайта».

Если срок SSL определить не удалось, в ячейке SSL появляется значок ⓘ. Подсказка к нему
объясняет причину: например, «Нет связи из сети монитора: таймаут подключения к порту 443;
резервная проверка: лимит запросов Globalping. Повтор через 15 мин». Причина хранится в
`latest_status.ssl_note`. Пустой результат не стирает последний известный срок и цепочку.
Сайты без данных проверяются повторно каждые 15 минут, без WHOIS. Полный цикл SSL+WHOIS
по-прежнему идёт раз в 4 часа.

Порядок QA/QC релизов описан в `QA_QC.md`.
